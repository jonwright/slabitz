# T04a: ExecuteSequences regression on stock zstd since b840caa

Status: review (no fix; regression documented)
Branch: `t04a-execseq-stock` (on `status-t04-t06`, which carries the task file)

## Result

- **The two aliasing views (`inoutUnCompressedFramesData32/16`) cost nothing.** The 439e2f2
  kernel with only the views added (variant f) is within 5 us of 439e2f2 on every cell.
- **On 439e2f2, b840caa's restructuring of MatchCopy costs 72-77% of the regression**
  (variant g). It splits into two parts, and both cost time:
  - moving the off=1 branch first: 53-72% (g2);
  - computing `copyLen` before the branch chain: 16-25% (g1).
- **On the current kernel, undoing the restructuring does not bring the time back.**
  - Restoring 439e2f2's branch order (h1, h2), or its whole prologue with the vector paths
    behind a cheap gate (h3), recovers at most 48 us of the gap (10%), and nothing on
    short_offsets.
  - Even with all three new paths switched off on top of that (h5), 76-78% of the gap is
    still there, and more than all of it on short_offsets.
  - The byte-copy loops (10 instructions) are identical in the SASS of 439e2f2, g1, g2 and
    main. The extra time is in the per-match code in front of them, spread over the whole
    MatchCopy and FusedCopy path, not in any single branch.
- **Why small edits matter here.** ExecuteSequences runs one 32-lane wave per frame and is
  latency-bound.
  - 207 us over about 32k matches per frame is about 6 ns, or about 15 cycles, per match:
    three or four dependent instructions.
  - The stock maskmax-1 cells are the ones with many short matches on the byte loop
    (128,456 matches in 4 silicon frames, T04).
  - The same per-match cost is invisible on pac frames, where the vector paths save far more.
- **No fix in the transform.** No variant recovers the stock time without losing the pac
  gains:
  - h3 recovers 23-33 us and makes pac 1-2% and short_offsets 2% slower;
  - h5 loses the pac gains entirely.

  The regression stays documented: AGENTS.md, T04 row.
- **For T20, which restructures ExecuteSequences anyway:** the per-match instruction count
  in front of the byte loop is what the stock cells pay for. More lanes per frame, or
  per-match work done in bulk before the copy loop, takes it off the critical path.
- **Kernels unchanged.** `build/sm_35` and `build/kernels` need no rebuild for T05.

## Method

- **Harness.** `bench/t04_runs.sbatch bisect 3`: every library runs once per round,
  interleaved, 3 rounds, in one Slurm job.
  - L40S `frcrg-gpu5l40s-01`, the baseline's node; 16 frames per call; cells `pac-zstd/`,
    `zstd3/`, `twin/silicon_zstd2`, `short_offsets`.
  - The gate checks every decode byte-exact against the expected output; all runs passed.
- **Tables.** Median over rounds of the per-round median; `±` is the run-to-run spread (max
  - min of the round medians). Made by `bench/t04_tables.py ... --metric
  kernel:ExecuteSequences`.
- **Variants.**
  - Each is one transform edit, kept as `bench/t04a_variants/var-*.patch`.
  - f, g, g1 and g2 are diffs against 439e2f2. f also patches
    `kernels/ExecuteSequences.slang` and `src/sbz_chain.c` to bind the views, as b840caa did.
  - h1-h5 are diffs against main 9de040d.
  - Built in `wt/t04-var-<x>`:
    - 439e2f2 based: `git worktree add` at 439e2f2, a `third_party/slang` link to
      `shared/slang`, `tools/build_all.py` and `make`, as T04 built `wt/t04-at-439e2f2`;
    - main based: `dev-root new` and `sbz build`.
  - The sbatch `lib()` resolves `var-<x>` to `wt/t04-var-<x>/build/libslabitz.so`.

| variant | base | change |
|---|---|---|
| f | 439e2f2 | the two views in the SRT, the kernel entry and the host binding, passed through every MatchCopy / FusedCopy call site, never used |
| g | 439e2f2 | b840caa's MatchCopy structure without views and vector paths: `copyLen` (with the `dstOfs < dstEnd` guard) first, off=1 branch first with a byte-store fill, then the long-offset byte loop, then the swizzle |
| g1 | 439e2f2 | only `copyLen` computed before the branches |
| g2 | 439e2f2 | only the off=1 branch moved first (`copyLen` computed inside each branch, as in 439e2f2) |
| h1 | main | long-offset branch tested first again (off=1 never takes it, since mlen >= 3) |
| h2 | main | h1, and `copyLen` / `isOff1` computed inside the branches instead of at the top |
| h3 | main | 439e2f2's prologue: long-offset branch first; inside it the vector paths only behind `offs >= 32 && mlen >= 32 && (offs & 3) == 0 && dstOfs >= offs`, otherwise 439e2f2's byte loop; off=1 fill and swizzle in the short branch |
| h5 | main | h2 with `false &&` on the off=1 fill and both vector copies |

## SASS

- **How.** `nvdisasm` from the `cuda/12.9.1` module, which is not in the slabitz
  environment, on each `exec.cubin`.
- **Byte loops.** The plain loop `dstData[i] = dstData[i - offs]` is identical in every
  kernel: 10 instructions (address arithmetic, `LDG.E.U8`, `STG.E.U8`, compare, branch).
  - 439e2f2, g1 and g2 have 17 inlined copies of it.
  - main has 23, its chunked vector paths adding the rest.
- **Size.**
  - 439e2f2: 634 branches.
  - main and h1: 995 branches, the same count in both. h1's reordering changes the order
    of the code, not its size.
- **Registers.** 50, no local memory (T04).

## Checks

- **Gate.** All 4 jobs ran without a `FAILED` line, so every decode was byte-exact.
- **Code.** No kernel or library change is proposed, so `sbz test` and the other suites
  are unaffected. The variants live only in `wt/t04-var-*` (scratch, not on any branch).
