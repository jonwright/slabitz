# T09: Decoder rejects, error codes, bounds

Status: review
Branch: `t09-rejects-bounds`
Executor: Claude

## Result

- **Valid zstd the decoder does not handle is rejected before any GPU work**,
  with the new code `SBZ_ERR_UNSUPPORTED = -7`:
  - any Dictionary_ID field, value 0 included: "frame N: dictionary (id K)";
  - a window of 2^29 bytes or more, including a single-segment content size
    that large: "frame N: window 2^k exceeds 2^29";
  - no Frame_Content_Size: "frame N: no content size".
- **More than 1 GiB of zstd output in one call** returns `SBZ_ERR_LIMIT`
  before any GPU work: "call output N bytes exceeds 1 GiB (1073741823); split
  the request". The 64-frame CeO2 twins (1,144,580,096 bytes) now give this;
  main gave CORRUPT "frame 0: status 0xa07a0006".
- **Block_Maximum_Size.** The host walk checks every block's size against
  min(window, 128 KiB), for raw, RLE (regenerated size) and compressed blocks.
- **Every frame stays inside its own output range.** A frame that decodes past
  or short of its content size, or a block that decodes to more than 128 KiB,
  gets a per-frame status. Its offending blocks are not written, so the
  neighbours stay byte-exact. The call returns CORRUPT, "frame N: decodes past
  its content size" (or "short of", or "a block decodes to more than 128 KiB").
- **A match reaching before its frame's start is caught** (`--patch-from`
  frames, and corrupt ones): CORRUPT, "frame N: match offset before frame
  start". Before, this was an illegal memory access (CUresult 700) for the first
  frame of a call, and a silent read of the previous frame's bytes for the
  others.
- **Both T07 GPU faults are gone.** The `--patch-from` frames of all 9 corpus
  versions return CORRUPT. A no-FCS frame in a context that decoded before is
  rejected on the host, and the context decodes a good frame afterwards.
- **Cost.** ExecuteSequences is unchanged. The new CheckSequenceOffsets kernel
  costs 9-48 us per call (+0 to +0.8% wall on the cells measured, see
  Performance). The gate passes.

## Design and deviations

1. **Host rejects** follow the settled design, in the GPU parser's order
   (dictionary, window, content size; `zstdgpu_FrameStatusFromHeader`). The GPU
   keeps its own checks.
2. **Output cap: host LIMIT, not lifting the GPU limit.** The DS limit
   (`kzstdgpu_MaxRequestUncompressedByteSize` = 0x3FFFFFFF) comes from 30-bit
   lookback values in the block-offset prefix sums; widening them touches every
   prefix kernel. The check is in `host_prepare`, so it covers
   `sbz_dctx_decompress`, `_frames` and bitshuffle-zstd. The 4 GiB checks
   further down stay as they were.
3. **Output bounds per block, not per write.** The task asked for a clamp in
   every writer. Instead, ComputeDestBlockOffsets (which already has the frame
   refs) checks each block against its frame:
   - a block that ends past the frame's content size: `OutputPastContentSize`;
   - the frame's last block ending before it: `OutputShortOfContentSize`;
   - a block over 128 KiB: `BlockTooLarge`.

   Such a block gets the offset `kzstdgpu_BlockDestOffs_Invalid` (0xFFFFFFFF)
   and is skipped by MemsetMemcpy and ExecuteSequences. Writes inside a block are
   already bounded by the block's end (`dstEnd`), so a block that fits cannot
   write outside it. This costs one compare per block instead of one per write.
   The short-of-content-size check goes beyond the task: libzstd rejects such a
   frame, and before T09 it left stale bytes in the output.
4. **The back-reference check is a separate parallel kernel.**
   - The first version checked each pair of sequences in ExecuteSequences' serial
     loop. The gate failed (job 38896821): ExecuteSequences +25% on
     `worst/min_matches` (7014 -> 8746 us) and +6.3% wall on three zstd19 CeO2
     u16 cells. That is the T04a lesson: this latency-bound one-wave-per-frame
     loop pays for every extra instruction per match.
   - `kernels/CheckSequenceOffsets.slang` does it in parallel instead: one
     256-thread group per compressed block, after FinaliseSequenceOffsets and
     ComputeDestBlockOffsets, before the writers. Each thread sums the
     `llen + mlen` of a contiguous slice of the block's sequences, a group scan
     gives each slice its start in the frame, and a second pass checks every
     match. A bad match marks the block invalid and sets `OffsetBeforeFrame`.
   - A single-wave version cost 631 us on `min_matches` (43k sequences per
     block); the 256-thread version costs 48 us.
5. **Status codes.** The new codes 0xA07A0007-0xA07A000A and the invalid-offset
   sentinel are added to `zstdgpu_shared_structs.h` by the transform. The host
   reads FrameStatus after stage 2 in exact calls. Queued calls already read it
   at the wait and replay exactly, so the replay gives the message. Messages
   name the status ("frame 1: decodes past its content size (status
   0xa07a0007)"), also for stage-1 statuses.
6. **Not done: naming the GPU status in the "block counts GPU != host"
   message.** The count pass that this cross-check follows does not write
   FrameStatus (`sbz_chain.c`, stage 0), so there is no status to name. Since
   the host rejects are now a superset of the GPU header rejects, a header
   reject can no longer reach this message.
7. **The no-FCS dctx-reuse fault.** Its likely cause: a queued (non-exact) call
   trusts the host's block counts. The GPU parser rejected the frame and wrote
   none of its block refs, so later kernels read stale refs from the previous
   call. I did not prove this; the trigger is gone because the host now rejects
   the frame. Any future GPU-only reject would reach the same path, and
   `run_frame_bounds.py` checks that every reject leaves the context usable.
8. **Files beyond the task's list:**
   - `kernels/CheckSequenceOffsets.slang` (new) and `tools/build_all.py` (its
     entry), `tools/build_fatbins.py` (count 22 -> 23);
   - `kernels/cpu_ref_bo.py` and `tests/run_bo_chain.py`: the bounds status
     against the CPU reference (3 new cases), and the kernel's new argument;
   - `tools/sbz.sh`: `run_frame_bounds.py` in `sbz test`;
   - `tools/gen_compat_corpus.py`: regenerated corpora get the new
     expectations;
   - `tests/data/frame_bounds/patchfrom_frame.zst`, moved from
     `tests/data/compat_bugs/` (removed with its README and base file);
     `tests/data/features_bugs/` removed (its only xfail is now an expected
     reject).
9. **Shared root.** `data/compat/manifest.json`: 45 entries changed to
   `reject:SBZ_ERR_UNSUPPORTED` (copy of the old one in
   `tmp/status-t04a-t07/data_compat_manifest.pre-t09.json`). Until this branch
   is merged, `run_compat.py --full` from `main/` reports those 45 as FAIL
   (main still returns CORRUPT). The committed subset is per branch and not
   affected.
