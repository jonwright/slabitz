Wall, ms per call: silicon_u32_maskmax-1 sync b840caa/0.1 2.555, main/0.1 2.437, main/0.2
**2.400** (IQR 0.008-0.027, spread <= 0.021).

- Same kernel, frames 0.1 -> 0.2: main 889.5 -> 858.0 us (-3.5%); every maskmax cell is equal
  or faster with 0.2 frames on the current kernel.
- Same frames, kernel b840caa -> main: 991 -> 889.5 us with 0.1 frames (-10%).
- The original pair (b840caa/0.1 = 1776 us vs 692e3f9/0.2 = 2321 us on the 1050 Ti) is here
  991 vs 858 us: **-13%, not +30%**. b840caa with 0.2 frames is slow (1328.5) as expected:
  merged off=P matches (copy length > offset) fell back to the byte loop before 692e3f9.
- Sequence statistics (`bench/t04_seqstats.py`, educational decoder, 4 frames): both versions
  carry the same bytes per class (off=1 3,684,578 B; off=P 67,641,272 B; literals 210,271 B).
  0.2 has 8009 fewer off=P sequences: 564 merged matches (mostly 14-16 planes each) that
  MatchCopy copies in 8412 plane-sized steps. Each zstd frame is one 32-lane wave that walks
  its sequences in order, and every step does the same `uint4` work as one unmerged match, so
  merging only removes per-sequence overhead (load, literal copy, branch). That matches the
  -3.5%.
- So of the three candidate causes: (a) the chunk loop is not more expensive per byte here;
  (b) merging does not move work between lanes or waves (one wave per frame, sequences in
  order); (c) the 1050 Ti pair mixed a kernel change with a frame change, from single runs.
  The per-lane histogram build from the Method was not made: there is no effect on the L40S
  to explain, and the statistics above show the per-wave work directly.
- **Open:** the 1050 Ti itself (6 SMs, 284 waves for 4 frames, so total work rather than the
  longest wave sets the time). `bench/t04_runs.sbatch q1q2` minus the Slurm lines is the
  recipe; it belongs to T05 (old cards, user hardware).

**Verdict: noise / measurement artefact on the L40S** (c); not reproduced, the current
kernel with pac 0.2.0 frames is the fastest combination measured.

| lz4/ceo2_u32_mask0/device | 0.258 (0.003, 0.003) | 0.097 (0.002, 0.000) | 0.079 (0.000, 0.000) | 0.060 (0.000, 0.000) |

All 52 CeO2 cells at all four sizes: `results/t04/38884599/q3-f*-r*.json`; the u16 and
maskmax-1 rows behave the same way. The frames are evenly spaced through the file at each
size (`np.linspace`), so the 1-frame call uses frame 0 only.

- **zstd (all three codecs, sync and async): per-frame time falls monotonically** with frames
  per call, 5-9x from 1 to 64. The old observation (rising per-frame time) came from a
  harness that joined the chunks inside the timed loop (T03 report); with the input built
  once it is gone. **Verdict: noise / harness artefact.**
- **Stock LZ4, host input: rises beyond 16 frames** (sync 0.277 -> 0.319 -> 0.485 ms). At 64
  frames the profiled upload is equal for lz4 and pac-lz4 (27.8 vs 28.5 ms for 252 / 249 MB),
  the GPU decode is *smaller* for lz4 (3.3 ms vs 7.3 ms), yet lz4's wall is 31.0 ms against
  pac-lz4's 19.2 ms. The device-input path for the same data falls (0.097 -> 0.060), and
  pac-lz4 (7x fewer blocks: 56 kB vs 8 kB) stays flat. So about 12 ms per 64-frame call is
  host-side and grows with the number of blocks faster than linearly. **Verdict: real,
  host-side; cause not measured** (hypothesis: the host block walk touches every 8 kB block
  header of a 252 MB input, which no longer fits the CPU cache, before the upload reads it
  again). The streaming use case (`AGENTS.md`: caller-owned device input) takes the device
  path, which does not have it. A host-side timer around the walk would settle it; noted
  for T13 (device-input API).
- **Found on the way:** at 64 frames the CeO2 zstd2 twins need 1,144,580,096 output bytes,
  above the 0x3FFFFFFF request limit (the gate caps only its re-encoded real cells, not `.h5`
  inputs), and the library reports `SBZ_ERR_CORRUPT` ("frame 0: status 0xa07a0006") instead
  of `SBZ_ERR_LIMIT`. This is the T09 item "make the host return LIMIT, call output exceeds
  1 GiB, before any GPU work" (`docs/dev/T09_decoder_rejects_bounds.md:94`); no new task.

## Question 4: fused vs unfused LZ4 across the gate matrix

`SLABITZ_LZ4_FUSED=0` against the default, the 80 LZ4 cells (pac-lz4, lz4, LZ4 twins and
worst cases; sync, async, device), main, 3 rounds; ratio = unfused / fused wall:

| group | cells | ratio range |
|---|---:|---|
| stock 8 kB blocks (lz4/*, twin/*lz4_8k*, worst/*lz4_8k*), where fused applies | 44 | **1.048 +- 0.011** (lz4/ceo2_u16_maskmax-1/async) to **2.687 +- 0.109** (lz4/silicon_u32_mask0/async) |
| pac-lz4 (56 kB blocks: fused never applies, same code both ways) | 36 | 0.988 to 1.013 |

The pac-lz4 group is a noise control: both runs execute the same kernels, and their ratios
stay within 1.2% of 1. **Verdict: confirmed, the fused path is never slower** on any cell of
the matrix; the smallest gain (5%) is CeO2 async, which is upload-bound.
