# T07: zstd version corpus: bitshuffle 0.4.0's zstd to 1.6.0

Status: review
Branch: `t07-zstd-versions`
Executor: worker (DeepSeek), reviewed by Claude

## What was built

A corpus that shows the GPU decoder reads what every relevant zstd encoder writes,
across the range from the zstd bundled in the first bitshuffle release with zstd
support (bitshuffle 0.4.0 -> its submodule `18d02cbf`, a v1.4.7-403 dev snapshot)
up to zstd 1.6.0. Two new scripts plus committed data:

* `tools/gen_compat_corpus.py` - builds the 9 zstd versions (CLI + libzstd) and the
  bitshuffle 0.4.0 shared library, then generates the corpus.  `--list`, `--build`,
  `--generate` (with `--full-only` / `--subset-only`).
* `tests/run_compat.py` - the runner.  Decodes each corpus file with the slabitz GPU
  decoder, checks it against its manifest expectation (byte-exact `decode` or a
  documented `reject:<code>`), and prints a version x mode table.  Each entry is
  decoded in its own subprocess (a GPU fault poisons the CUDA primary context for
  the whole process - see T06 - so decoding all of a version's files together would
  cascade a single corrupted frame into every later file of that version).  A
  manifest entry whose file is missing on disk is reported as `missing file: <path>`
  and counted as FAIL, not as a worker crash.
* `tools/sbz.sh` - added `run_t tests/run_compat.py` to `cmd_test` so the committed
  subset runs inside `sbz test`.
* `tests/data/compat/` (committed subset, 2.4 MB < 5 MB) + `manifest.json`.
* `tests/data/compat_bugs/` - the one FAIL's reproducer + `README.txt`.

The corpus:

* FULL: `$SLABITZ_DEV_ROOT/data/compat/` (shared root, this task owns it): one file
  per (version, mode, input), 283 entries (279 zstd + 4 bitshuffle), 119 MB on
  disk, manifest `data/compat/manifest.json`.
* SUBSET: `tests/data/compat/` (committed): per version the level-3 and level-19
  text and detector inputs, the no-FCS (`streaming`) and window-30 (`long30`)
  expected-reject cases, and the bitshuffle 0.4.0 chunks; 58 entries, 2,555,414 bytes.

### Corpus inputs

Every CLI mode runs on the 120 KB text input as before, and in addition, for every
version:

| input | what | used for modes |
|---|---|---|
| `det_u16` | silicon u16 detector frame crop (`SLABITZ_EXAMPLES`, 2162 x 512, raw little-endian, 2,213,888 B) | level1, level3, level19, ultra22, check, B65536 |
| `det_u32` | CeO2 u32 detector frame crop (2162 x 512, raw little-endian, 4,427,776 B) | level1, level3, level19, ultra22, check, B65536 |
| `random` | 1 MB incompressible, fixed seed (`numpy.default_rng(20261127)`) | level3, level19 |
| `det_multi` | 6 repeated CeO2 u32 crops with a small per-frame change (26,566,656 B, >= 24 MB) | T0 |

Modes and frames, per version (text input unless noted):
`level1/3/9/19`, `--ultra -22`, `--long=27` (150 MB zeros -> window 2^27, decodes),
`--long=30` (1.2 GB zeros -> window 2^30, reject), `--long=31` (2.2 GB zeros ->
window 2^31, reject), `-T0`, streaming via stdin (`-c`, no FCS -> reject),
`--no-content-size` (no FCS -> reject), `--check`, `--no-check`, `-B65536`,
`--patch-from=<base>` (reject), `-D <dict>` (reject), and the detector/random/T0
inputs above.

Plus 4 bitshuffle-0.4.0 filter-32008 chunks (zstd `18d02cbf`): the silicon u16 and
CeO2 u32 detector crops at the 0.4.0 default block (8192 B) and at the real file's
256 KB / 64 KB blocks.  `cd_values` are `[0, 4, elem, block, 3, level]`, exactly as
bitshuffle 0.4.0's `bshuf_h5_set_local` writes them; the chunk header records the
resolved `block * elem` bytes (the 8192-byte default when block=0), as
`bshuf_h5filter.c` writes it.

A mode an old CLI lacks is recorded as `n/a` in the manifest (detected by the CLI's
error), not as a failure.  In this sweep every version supported every mode, so the
whole table is filled.

## Decoder bug (FAIL) - #1: --patch-from frames fault the GPU

**Reproducer:** `tests/data/compat_bugs/` - `patchfrom_frame.zst` (1432 B),
`patchfrom_base.bin` (20000 B), `README.txt`.

A frame written by `zstd --patch-from=<base>` (a valid zstd frame with no
Dictionary_ID that libzstd decodes when the base is given back) crashes the slabitz
GPU parser instead of being rejected:

```
sbz_dctx_decompress_frames: readback Counters: cuMemcpyDtoHAsync failed:
  CUresult 700 (an illegal memory access was encountered)
```

**What the frame does that faults.**  A `--patch-from` frame is compressed with the
base file as an out-of-band prefix: the first sequences in the frame reference data
that lies *before* the frame content (inside the base).  The educational decoder
(`tools.edu_oracle`) decodes the frame far enough to resolve those match offsets and
then stops: the first resolved byte offset is 389 while only a handful of bytes have
been produced, i.e. **the match offset is larger than the bytes produced so far in
the frame**, and its strict bounds check fails with `Error: Corruption detected while
decompressing`.  The slabitz GPU decoder does not bounds-check the match offset
against the bytes decoded so far (it only trusts the compressed-block contents, the
known 2026-11-25 limit) and reads out of bounds, hence `CUresult 700`.  This is a
hard GPU crash (SBZ_ERR_BACKEND) that poisons the CUDA primary context for the whole
process, and it reproduces with every corpus version (the frames differ only by
encoder).  libzstd decodes the same frame to 120146 bytes (sha256
`b253970ede89791ac51db93a57e331810ce63cf02c87bcc4119d015ac74e9228`) when given the
base.  Expected: `reject:SBZ_ERR_CORRUPT`.

**Input for two tasks, not one:** T09 should make the decoder **reject** a patch-from
frame (as it already rejects a Dictionary_ID frame) with `SBZ_ERR_CORRUPT - the
frame needs an out-of-band prefix that the decoder does not carry; and T11 (GPU
corrupt-input sanitizer) should turn the bad-offset **fault** into a clean error
rather than an illegal memory access.  The decoder was **not** changed (task rule).

The no-FCS, window-30/31, dictionary frames **do** reject cleanly with
`SBZ_ERR_CORRUPT` when decoded in a fresh dctx.  (Note: an important finding is that
a no-FCS frame decoded in the **same** context after a normal frame faults the GPU -
a dctx-reuse bug.  T06/T09 territory; recorded, not fixed.  The runner sidesteps it
by using a fresh dctx per entry, which is why the table's `streaming`/`nocontent`
cells show `reject` rather than a cascade.)

## Decisions taken

1. **The window cases use large *zero* files, generated on the fly.**  `--long=27`
   (window 2^27) needs content > 2^27 to be multi-segment; `--long=30` needs
   content > 2^30; `--long=31` needs content > 2^31.  Zeros compress to a few KB
   while still producing the large-window multi-segment frame header, so the corpus
   stays small and the 1.2 GB / 2.2 GB inputs are never stored (only hashed).  The
   window-30 subset file is 43 KB.
2. **One subprocess per entry, not per version.**  The task said "each version's files
   decoded in a separate subprocess", but a corrupted frame (the patch-from fault)
   poisons the CUDA primary context for the whole process (T06), so per-version
   grouping would falsely FAIL the rest of that version's files (the dictionary entry
   that actually rejects cleanly).  Per-entry isolation reports the fault on exactly
   the entry that caused it.  Documented as a deviation.
3. **Fresh dctx per entry inside the worker.**  Even within one process, a no-FCS
   frame faults the GPU when decoded after a normal frame on the same dctx; a fresh
   dctx per entry makes it reject cleanly.  This is a real dctx-reuse bug recorded for
   T09, not worked around by changing expectations.
4. **The bitshuffle-0.4.0 "default" blocks resolve the default before writing the
   header.**  bitshuffle 0.4.0's `bshuf_default_block_size` is 8192 bytes / elem
   (rounded to a multiple of 8, min 128).  `sbz_dctx_bshuf_decompress` rejects a
   chunk whose `block bytes` header is 0, so the generator records the resolved
   block (8192 B for u16 and u32) in the header while keeping `cd_values[3]=0`, and
   calls `bshuf_compress_zstd` with the resolved block - exactly what `bshuf_h5filter.c`
   does.
5. **Reference SHA-256 of a frame = SHA-256 of the original input.**  zstd and
   bitshuffle are lossless, so `decoded_sha256 = sha256(input)` without decoding.
   The `--full` run additionally re-decodes every decode entry with the version's own
   CLI and the v1.6.0 CLI to confirm the manifest reference is right (`reference_failures=0`).
6. **The `--long=27` reference must be decoded by the CLI, not assumed equal to the
   input.**  It decodes to the 150 MB zero source; that is within the 1 GiB output cap
   and only one frame per version, so the full run stays fast and the cross-version
   check covers it.
7. **`n/a` is detected from the CLI's error.**  If a version's CLI rejects a mode the
   generator would write, the entry is recorded `n/a` (no file) rather than failing.
   Here no version rejected a mode.
8. **Detector / random / multi-job inputs were added per the review.**  Raw
   little-endian detector crops (u16 + u32) at level1/3/19, ultra22, check and B65536,
   a 1 MB fixed-seed incompressible random input at level3/19 (covers raw blocks),
   and a >= 24 MB multi-frame detector input for `-T0` (with a small per-frame change
   so the encoder really splits jobs) - see the corpus-input table.  The subset uses a
   smaller detector crop (the 2,213,888 B u16 frame) at level 3 and 19 to stay under
   5 MB (2.4 MB total).
9. **Missing-file handling.**  A manifest entry whose file is not on disk is reported
   as `missing file: <path>` and counted as FAIL, so a manifest/data mismatch is
   obvious instead of surfacing as a garbage "worker crashed" subprocess.

## Deviations from the task file

* Per-entry subprocess isolation (see decisions 2) instead of per-version, so a real
  GPU fault is attributed to the frame that caused it.
* `ZSTD_compressSequencesAndLiterals` was added in v1.5.7 per the CHANGELOG, not v1.6.0
  (the task file said v1.6.0).  Recorded verbatim; the T19-encoder relevance is the same.
* `tests/test_suite.py` was not edited: it auto-discovers scripts from the `run_t
  tests/*.py` lines of `tools/sbz.sh`, so adding the line there is sufficient (as T06
  did for run_features.py).
* The detector crops are raw little-endian frames (no bitshuffle), written straight to
  the CLI; the bitshuffle chunks are a separate kind.  This matches the review: the
  "detector images" input is a plain detector frame, not a filter-32008 chunk.
* `docs/dev/README.md` status update (set T07 to review) is left to the reviewer
  (README.md is not in "Files that may change").
