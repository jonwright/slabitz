## Method

**Canary.**  The decoder owns its output buffer, so a caller cannot pad it.  The
canary is a memory *neighbour*: each mutant is decoded in **one** call between
two unmodified good frames/chunks

* `sbz_dctx_decompress_frames` (stock zstd single frames),
* `sbz_dctx_bshuf_decompress` (pac-zstd chunks),
* `sbz_dctx_bslz4_decompress` (bitshuffle-LZ4 chunks),

and the two neighbours (frame A at offset 0, frame B at `csA+csM`) are compared
byte-exact against the good input's own decode.  The decoder lays the three
frames out by their content sizes (`UnCompressedFramesRefs[f].offs` = running sum
of `frame_infos[].uncompSize`, `src/sbz_chain.c:939`), so the middle frame's
region is `[csA, csA+csM)` and the second neighbour starts at `csA+csM`
(`csA`/`csM` are the Frame_Content_Size / chunk header total, read from the
frame/chunk header, **not** the padded buffer length).  A mutant that overruns
its own slot damages the second neighbour; both neighbours matching the
reference means the canary is intact.  Writes outside the whole allocation are
compute-sanitizer's job.

**Mutations** (all four kinds), only inside compressed blocks (block type 2),
found with a Python walk of the frame header + 3-byte block headers (the walk is
cross-checked once per seed frame against `sbz_dctx_parse`, no error):

* `bit` - one bit flipped,
* `zero` / `ff` - one byte set to 0x00 / 0xFF,
* `run8` - a run of 8 random bytes,
* `trunc` - drop the last 4 bytes of a block, its block-header size field lowered
  by 4 (a Frame_Content_Size is left as it is, so the frame then lies about its
  size).

For bitshuffle-LZ4 only the LZ4 block payload bytes are touched (never the chunk
or block-record headers); for pac-zstd chunks a compressed block inside a chunk's
zstd frame is mutated and the chunk is re-encoded (the outer `[BE u32 c]` record
sizes are updated for `trunc`).

**Isolation.**  One subprocess per input (a GPU fault poisons the CUDA primary
context for the whole process, verified here: after the `t07-patchfrom` fault a
fresh `sbz_dctx_create_cuda` in the *same* process already fails with CUresult
700), each under `timeout 20`; up to **4 subprocesses in parallel** on the same
GPU.  The parent precomputes each base's reference decode once (7 bases) and
spawns worker subprocesses.

**Result per input**, exactly one of:

| result | meaning |
|---|---|
| `ok-identical` | rc == 0, neighbours intact, the middle decoded to the original bytes (the mutation did not matter) |
| `error-code` | rc < 0 with a normal sbz error (the code is recorded) |
| `wrong-output` | rc == 0, neighbours intact, but the middle decodes to different bytes (zstd checksums are not verified on the GPU) |
| `canary-hit` | **rc == 0** but a neighbour differs -> an in-buffer out-of-bounds **write** (REQUIRED ZERO) |
| `err-neighbour` | rc < 0 AND a neighbour differs (counted and reported, not failed: output is undefined after an error today; T09 adds per-frame bounds) |
| `gpu-fault` | the call returned an error whose message contains a `CUresult` (`CUresult 700`); the process can no longer use the GPU (REQUIRED ZERO) |
| `crash` | subprocess killed by a signal or nonzero exit without a result line (REQUIRED ZERO) |
| `hang` | the `timeout 20` expired (REQUIRED ZERO) |

**Inputs & mix.**  Stock zstd levels 3 and 19 (`tests/data/compat/v1.5.7--level{3,19}_det_u16.zst` and
`v1.5.7--level{3,19}_text.zst`), the pac-zstd fixtures (`data/pac/*zstd*.chunk.bin`, the
fixtures `run_pac_fixtures.py` decodes), and bitshuffle-LZ4 chunks
(`data/pac/silicon_u16_lz4.chunk.bin`, a bslz4 chunk `run_pac_fixtures.py`
decodes through `sbz_dctx_bslz4_decompress`).  The container type is drawn with
the brief's mix **40% stock zstd / 30% pac zstd / 30% bitshuffle-LZ4**, then a
base uniformly within that type; the mutation kind uniformly from the four.
Default **2000** random inputs + the 8 named seeds = **2008** total; `--long`
= 20000; `--n`/`--seed`/`--jobs`/`--replay`/`--sanitize` options provided.

## Decisions taken

1. **Fixed default seed `20261127`** (recorded), and **deterministic**: two runs
   with the same seed give identical counts (see verification #3).
2. **One subprocess per input, at most 4 in parallel** on the same GPU (recorded;
   the brief allows this).
3. **The reference for the good neighbours is decoded once per base in the
   parent** and shipped to each worker as a `.bin`; `--replay` re-derives it from
   the committed base file so a saved failure needs nothing else.
4. **The neighbour/middle region sizes are the frame content size / chunk total,
   not the padded output-buffer length** (a single frame decode pads the buffer
   to 4 bytes, e.g. 120146 -> 120148 for the level3-text frame; using the padded
   length silently shifted the second neighbour's offset by the padding and gave
   false canary-hits).
5. **`err-neighbour` is counted but not saved** (output is undefined after an
   error; the brief classifies it as reported, not failed), and **not** a
   required-zero item.
6. **The middle-frame "ok-identical" check is opt-in** (a `check_middle` flag):
   it is on for byte-mutations of a base (where the expected middle output is the
   base's own decode) and off for the hand-built RLE-literals seed (whose
   expected output is not well-defined).
7. **`t07-patchfrom` is decoded alone** (`sbz_dctx_decompress`, a single frame)
   as the brief says; the other named seeds are byte-mutations and use the triple.
8. **The offset-code mutation (make the first match of a valid frame reach before
   the frame start) is SKIPPED.**  It is not simple: it means re-encoding the
   first sequence's offset FSE bitstream so the resolved offset exceeds the bytes
   produced so far.  The `--patch-from` seed and the `pac-silicon-u16-zstd`/`trunc`
   gpu-faults already exercise the same "a match reaches before the frame /
   before the bytes produced" mechanism (CUresult 700), so the mechanism is
   covered; building the synthetic offset mutant is left as a follow-up if the
   reviewer wants it.
9. **A truncated block in a pac-zstd chunk** is done by dropping the last 4 bytes
   of the inner zstd compressed block and lowering its 3-byte block header, then
   re-encoding the chunk (the outer record size shrinks accordingly), so the
   frame still passes the host walk on the *structure* but lies about its size.
10. **The 8-byte/`0x00`/`0xFF` and 8-byte-run mutations choose the free byte
    offset inside the block**; `run8` clamps to the block so it never runs past
    the block body.  A mutant must have a compressed block of at least 8 bytes to
    be built (else the input is skipped, never wrongly mutated).

## Distinct root causes (one section per cause; reviewer -> T11a task files)

The 310 canary-hits + 81 gpu-faults group into **two** decoder defects plus one
**sanitizer** finding.  I group by failure mechanism and message (deepest
kernel-level root-cause needs the kernel source, which per the rules I did not
modify or dissect); each section names its reproducers (saved under
`build/corrupt_cases/`, gitignored, **not committed**).

### 1. In-buffer output overrun into the next frame/chunk (`canary-hit`, rc == 0)

**310 inputs.**  A corrupt compressed block makes the Stage-2 decoder write more
bytes than the frame's content size (or a chunk's `total`), so it overruns its
own slot and overwrites the **next** frame's/chunk's slot in `UnCompressedFramesData`
/ `BshufOutput`.  Verified for a representative: for `canary-hit-0.bin`
(`v1.5.7-l3-det/zero`) the call returns rc 0, the output length equals the sum of
the three content sizes, frame A is intact (== reference), the middle region is
wrong, and frame B's region does **not** match the reference at its content-size
offset (`ref` occurs only at offset 0) -> frame 1 overwrote frame 2.  This is the
documented known limit "decoded size is not checked against FCS, so a lying frame
can overwrite its neighbour" (AGENTS.md / T09).

* Reproducers: `build/corrupt_cases/canary-hit-0.bin` ... `canary-hit-309.bin`.
* By base: v1.5.7-l19-det 114, v1.5.7-l19-text 104, v1.5.7-l3-det 59,
  v1.5.7-l3-text 14, pac-ceo2-u32-zstd 12, pac-silicon-u16-zstd 7.  (Both
  stock-zstd frames and bshuf chunks; the bslz4 chunk produced 0.)
* By mutation: trunc 96, run8 69, ff 58, zero 46, bit 41.
* **Does not get caught by memcheck** (the write is inside the whole allocation,
  just past the frame's logical slot) - this is exactly why the neighbour canary
  was added.

### 2. GPU illegal memory access (`gpu-fault`, `CUresult 700`)

**81 inputs.**  The call returns an error whose message contains `CUresult 700`
("readback Counters: cuMemcpyDtoHAsync failed ... an illegal memory access was
encountered"), and the process can no longer use the GPU.  This is the class of
the documented limit "the kernels still trust compressed-block contents" and the
T06/T07 faults (patch-from offset before frame start; repeat FSE table with no
previous table).  Reproducers `gpu-fault-0.bin` .. `gpu-fault-80.bin`.

* By base: pac-silicon-u16-zstd 59, pac-ceo2-u32-zstd 14, v1.5.7-l19-det 3,
  v1.5.7-l19-text 2, v1.5.7-l3-text 1, t07-patchfrom 1, t06-repeat-LL-first 1.
  -> the **bitshuffle-zstd chunk path** dominates (73/81): corrupting a compressed
  block inside a chunk's zstd frame very often reaches an illegal memory access.
* By mutation: trunc 26, run8 25, ff 14, zero 7, bit 7.
* The two named seeds (`t06-repeat-LL-first`, `t07-patchfrom`) are the known
  faults; the 79 random ones are new triggers on the same "trusted block content"
  mechanism.

### 3. compute-sanitizer memcheck: OOB read in the Stage-2 zstd kernel on a VALID frame

A single **unmutated** stock frame (`v1.5.7--level3_text.zst`, decoded by
`sbz_dctx_decompress`) makes memcheck report, 76 times (one per accessing
warp-lane) and with the decode then failing the launch (719) because of the
flagged access:

```
========= Invalid __global__ read of size 1 bytes
=========     at main_0+0xe0f0
=========     by thread (20,0,0) in block (0,0,0)
=========     Access at 0x... is out of bounds
=========     and is 1 bytes after the nearest allocation at 0x... of size 440 bytes
=========     Host Frame: cuda_launch -> launch -> stage2 -> sbz_dctx_decompress
```

The host backtrace names `sbz_dctx_decompress`, i.e. the **Stage-2** (sequence
execution / copy) kernel reads 1 byte past a 440-byte allocation on a **valid**
frame.  It is benign for the output of this input (the byte read is not used
destructively) but it is a genuine out-of-bounds read.  This is a distinct defect
from #1/#2, found only because memcheck inspects every kernel load.

* Reproducer: decode the valid frame under memcheck, see verification #5.

* The **`memcheck` OOB read on the valid zstd frame** is the sanitizer finding; it

* The fuzz `--sanitize 200` "fault tripped" (exit 1) is the fuzzer's single-process

## Follow-ups for the reviewer (T11a task files)
