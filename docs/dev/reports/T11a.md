# T11a: ExecuteSequences reads past the end of the literals

Status: review
Branch: `t11a-literal-overread` (on `t11-gpu-corrupt`)
Executor: Claude

## Result

- **The memcheck errors on valid frames are gone.** `tests/run_sanitizer.sh`:
  memcheck 0 errors on the zstd text frame, which had 76 before. The
  bitshuffle-zstd and both bitshuffle-LZ4 cases also have 0 errors, and
  racecheck shows 0 hazards everywhere.
- **The fix is host-only.** `src/sbz_chain.c` allocates 64 bytes of slack
  behind both literal sources:
  - `DecompressedLiterals` (Huffman-coded literals);
  - `CompressedData` (raw literals; the zstd and bitshuffle-zstd paths, through
    `stage0`).
- **No kernel change.** The fused copy fast paths keep their unconditional
  literal loads. T04a showed that a per-lane guard in that loop would cost time.
- `buf_size_slack` allocates the slack without changing the buffer's size. The
  element count bound to kernels and what `sbz_dctx_read_buffer` returns are as
  before.

**Before the fix**, on main bb081d1, the same memcheck case gave 76 one-byte
reads 1 to about 30 bytes past the 440-byte `DecompressedLiterals` allocation,
in ExecuteSequences (`SLABITZ_DEBUG_SYNC=1`: `chk:Execute`). That run stands in
for the reviewer check "remove the padding".

**Not padded:** the caller's device input of the LZ4 device path (`ext_cd`).
Only the LZ4 kernels read it, never ExecuteSequences.

**Deviation:** the slack is not zero-filled. The loaded values are never used,
and memcheck checks bounds, not initialisation.
